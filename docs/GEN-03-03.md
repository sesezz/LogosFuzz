# GEN-03-03: Mocking 코드 삽입 — 제거됨

**이 단계는 삭제했다.** 대상이 Bazel 로 빌드하는 S-CORE 로 바뀌면서 존재 이유가
사라졌기 때문이다.

## 무엇을 지웠나

| 지운 것 | 대체 |
| --- | --- |
| `logosfuzz/generate/gen_03_03_mock_injector.py` | 없음 (Bazel `deps` 가 링크를 책임진다) |
| `tests/test_gen_03_03_mock_injector.py` | 없음 |
| `logosfuzz/pipeline.py` 의 GEN-03-03 단계와 `--no-mock` 옵션 | 없음 |
| `pipeline.py` 의 `build_signature_map` / `collect_undefined_symbols` | 없음 (위 단계 전용 헬퍼였다) |

## 왜 지웠나

이 단계는 **링크 단계에서 미정의 심볼이 남는 문제**를 풀려고 만든 것이다. 하네스를
`clang` 으로 직접 컴파일·링크하던 시절엔 대상이 다른 번역 단위의 함수를 부르면
컴파일은 통과하고 링크만 깨졌다. dlt-daemon 이 정확히 그 경우로, `dlt_common.c` 가
`dlt_log.c` 의 함수 6개를 불러 하네스 65개가 전부 컴파일 65/65 · 링크 0/65 였다.
그 미정의 심볼에 stub 을 꽂아 넣는 것이 `insert_mocks` 의 일이었다.

Bazel 에서는 이 문제가 애초에 생기지 않는다. `deps` 가 링크 대상을 전부 선언하므로
필요한 번역 단위가 빠질 수 없고, 빠지면 그건 stub 으로 덮을 문제가 아니라
**`deps` 가 틀렸다는 신호**다 — 그리고 그건 GEN-03-02 자가치유가 분류해서 고친다
(`missing_dep` → `add_deps`). stub 을 꽂으면 오히려 진짜 결함을 가린다.

자동차 환경 가상화(CAN/UDS) 목적의 모킹도 함께 없앴다. 대상이 S-CORE 의 `//score/json`
같은 순수 라이브러리라 ECU·네트워크 인터페이스를 가상화할 일이 없다.

## 남아 있는 흔적

- `logosfuzz/generate/contracts.py` 의 `HarnessArtifact.expected_mock_symbols` 필드와
  `validation.py` 의 `mock_trace` 단계는 **남겨 뒀다**. 아무도 이 필드를 채우지 않으므로
  이 단계는 항상 통과한다. 모킹이 다시 필요해질 때를 위해 계약만 유지한다.
- `logosfuzz/execute/sanitizer.py` 는 아직 `mocking-fail-fp` 결함 종류를 만들고,
  `logosfuzz/analyze/triage.py` 는 그걸 오탐으로 판정한다. 이 정리는 C 파트의
  "차량특화 죽은 분류 제거" 항목에 속한다.
