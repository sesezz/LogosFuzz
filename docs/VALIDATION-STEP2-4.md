> 대상 저장소: `origin/dev` 기준 브랜치 `validation/step2-step4`

### 1.1 격리 실행 버그 — 실증

```
$ docker run --rm --entrypoint bash nginx:stable -lc bash -lc "echo X"
(출력 없음)
exit=0        <- 실행되지 않았는데 성공으로 보인다

$ docker run --rm nginx:stable bash -lc "echo X"
X
exit=0
```

수정된 이미지에서 실제 하네스가 **6,655,739회 / 7,387 exec/s** 로 동작하는 것을
확인했다(§3).

### 1.7 하네스 품질 게이트

2·4단계에서 "컴파일 성공"으로 집계된 하네스가 첫 입력에 죽는 일이 반복됐다.
세 가지를 막는다.

**(a) 실행 불가를 만드는 C 경고를 에러로.**
`dlt_print_char_string` 의 시그니처는 `char **text` 인데 하네스가 `char *` 를
넘겼다. C 에서 이건 **경고**라 빌드가 성공하고, 파이프라인은 `returncode == 0`
이고 로그에 `error:` 가 없으니 성공으로 센다. 지금의 "하네스 컴파일 성공률"은
"링크까지 통과했다"는 뜻이지 "실행 가능한 하네스"라는 뜻이 아니다.

```
-Werror=incompatible-pointer-types      char* <-> char** 등 포인터 층위 불일치
-Werror=implicit-function-declaration   선언 없이 호출 -> 잘못된 시그니처로 링크
-Werror=int-conversion                  정수를 포인터 자리에 전달
-Werror=return-type                     LLVMFuzzerTestOneInput 이 int 를 안 돌려줌
```

**넣자마자 실제 결함을 잡았다.** 2단계 1차 시도에서 생성된 하네스가
`png_set_io_ptr` 을 호출했는데, 확인해 보니 **libpng 에 존재하지 않는 함수**였다
(`png_get_io_ptr` 만 있다).

**(b) 대상 함수 재선언 제거.** 프롬프트로 금지해도 계속 재발했다. 후처리로
지우되, **초안에만 걸면 소용이 없다** — 수정 라운드에서 LLM 이 같은 선언을 다시
써 넣어 에러가 부활한다. `SelfHealLoop(sanitize=)` 훅으로 모든 라운드에 적용한다.

**(c) 언어 판별.** SCH 는 언어를 구분하지 않아 C++ 전용 API 가 C 그룹과 나란히
나오고, C 로 컴파일하면 원인과 동떨어진 에러가 뜬다.

### 1.8 테스트 코드 표시

Eclipse S-CORE `logging` 저장소를 색인했더니 API 388개 중 **187개(48.2%)가
테스트 코드**였고, SCH 가 뽑은 최우선 로직 그룹이 전부 gtest 픽스처
(`SetUp`/`TearDown`)였다. `is_static` 과 같은 원칙으로 `is_test` 를 기록한다 —
KB 는 사실만 기록하고 거를지는 소비자가 정한다.

판정은 **디렉토리 세그먼트와 파일 이름**으로 한다. 처음에는 절대 경로 전체에
부분 문자열 매칭을 했는데 상위 디렉토리 이름에 우연히 "test" 가 있으면 제품
코드를 오판했고, 회귀 테스트가 그걸 잡아냈다.

## 2. ANA-05-01 정탐/오탐 판별 — 10% → 85%

### 2.1 정답셋 정정 (1단계 리포트의 오류)

1단계에서는 노션 문서를 근거로 `id_000001`/`id_000188`(`dlt_filter_delete_v2`)를
**오탐**으로 놓고 5건을 측정했다. 같은 크래시를 더 깊이 분석한 4팀 보고서는 이
둘을 **정탐**으로 판정한다 — 공개 API 계약을 하나도 어기지 않는 정상 호출 2줄로
재현되기 때문이다(CWE-125).

**1단계 리포트의 60% 수치를 인용 중이라면 수정이 필요하다.** 같은 보고서가 근거와
함께 판정한 **20건(정탐 2 / 오탐 18)** 으로 정답셋을 교체했다.

그 보고서는 "in-tree 호출부 0건"이 도달 불가를 뜻하지 않는다고 명시한다 —
의도된 호출자가 libdlt 를 링크하는 서드파티 애플리케이션이기 때문이다. 이 지적은
이번에 추가한 신호 하나와 정면으로 배치되어 그 신호를 폐기했다.

### 2.2 무엇을 바꿨나

`logosfuzz/analyze/reachability.py`(신규)가 판정하지 않고 **증거만** 모은다.

| 증거 | 무엇을 판단하는 데 쓰나 |
| --- | --- |
| 크래시 함수의 정의·링키지·결함 라인 주변 소스 | 무엇을 읽거나 쓰다 경계를 벗어났는가 |
| 호출부를 프로덕션 / 하네스·테스트로 분리 | 제품 경로에서 도달하는가 |
| 크래시를 낸 하네스 소스 | 하네스가 API 계약을 어겼는가 |
| **결함 라인이 읽은 필드에 값을 쓰는 API 의 본문** | 계약을 지킨 경로로도 그 값이 나오는가 |

마지막 항목이 판정을 가른다. "하네스가 계약을 어겼다"는 오탐의 충분조건이
아니다. 계약을 어긴 하네스가 찾아낸 버그라도 계약을 지킨 호출로 같은 값이
만들어지면 실제 결함이다.

### 2.3 측정 (정답 20건, gpt-4o-mini, 3회 반복)

| 구성 | 정확도 | 정탐 재현율 | 오탐 재현율 | 오탐→정탐 오분류 |
| --- | --- | --- | --- | --- |
| `rule_plain` (개선 전) | 2/20 (10%) | 2/2 | 0/18 | 9건 |
| `rule_ctx` (규칙 + 신호) | 2/20 (10%) | 2/2 | 0/18 | 9건 |
| `llm_baseline` (1단계 프롬프트) | 2/20 (10%) | 2/2 | 0/18 | 18건 |
| **`llm_ctx` (새 프롬프트 + 증거)** | **17/20 (85%)** | 1/2 | **16/18** | **1건** |

3회 반복에서 판정이 갈린 케이스 0건.

- 규칙 기반은 오탐을 하나도 잡지 못한다(0/18). 한계는 프롬프트가 아니라 판정에

- 개선의 대부분은 증거 주입에서 나온다. 모델·온도가 동일한데 10% → 85%.
- 남은 오류 1건은 `id_000001` 과 증거가 동일한데도 판정이 갈린다. gpt-4o-mini 의
  추론 한계로 보인다.

### 2.4 한계

## 3. 2단계 — Magma libpng 기반 정량 비교

### 3.1 비교 설계

LogosFuzz 의 기여는 새 뮤테이션 엔진이 아니라 **하네스 생성**이다. 퍼저를 바꿔가며
비교하는 것은 이 도구를 재는 게 아니다. 엔진·대상·시드·시간을 고정하고
**하네스만** 바꿨다.

| 고정 | Magma libpng(ground-truth 버그 7건), libFuzzer, 시드 4개, 900초 |
| --- | --- |
| 베이스라인 | OSS-Fuzz `libpng_read_fuzzer` — 사람이 작성해 오래 쓰인 표준 드라이버 |
| LogosFuzz | 같은 라이브러리에 대해 GEN 이 자동 생성한 하네스 |
| 측정 | 버그 도달/발현(Magma 카나리), 커버리지, 실행량 |

Magma 정식 경로(`tools/captain/build.sh`)는 libFuzzer 를 위해 LLVM 저장소를
통째로 클론한다. 여기서는 clang-14 내장 libFuzzer 를 쓰고 Magma 에서는
**ground-truth 버그 패치와 카나리 매크로만** 가져왔다. 비교 근거인 "어느 버그에
도달/발현했는가"는 그대로 유지된다.

### 3.2 결과 — 3회 반복 (각 900초)

**단발 측정으로는 아무것도 말할 수 없었다.** 1차 비교에서 베이스라인은 바이너리도
옵션도 시드도 바꾸지 않았는데 재실행 시 실행량이 −47% 흔들렸다. 그래서 같은
조건으로 3회씩 반복했다.

두 구성에 **동일한 메모리 상한**(`allocator_may_return_null=1`,
`max_allocation_size_mb=512`)을 걸었다. 이 PC 는 가용 메모리가 2GB 남짓인데
LogosFuzz 하네스 피크가 2.4GB 라, 상한이 없으면 그쪽만 스왑에 걸려 비대칭으로
느려진다. 절대 처리량은 약 30% 낮아지므로 상한 없이 잰 1차 수치와는 직접
비교하지 않는다.

| | 실행 (평균 ± SD) | 커버리지 (평균 ± SD) | 버그 발현 |
| --- | --- | --- | --- |
| 베이스라인 | 3,331,061 ± 2,360,862 | **1,258 ± 161** | PNG003, PNG006 (3/3) |
| LogosFuzz | 3,366,739 ± 1,482,255 | **887 ± 25** | PNG003, PNG006 (3/3) |

```
베이스라인 r1 execs=2,954,667 cov=1215   LogosFuzz r1 execs=2,114,931 cov=861
베이스라인 r2 execs=5,857,508 cov=1437   LogosFuzz r2 execs=2,981,796 cov=890
베이스라인 r3 execs=1,181,008 cov=1123   LogosFuzz r3 execs=5,003,490 cov=910
```

**세 가지로 읽는다.**

1. **실행량은 차이가 없다.** 평균이 3.33M 대 3.37M 로 사실상 같은데 표준편차가
   평균만큼 크다. 이 지표로는 우열을 말할 수 없다. 1차·2차 측정에서 "누가 더
   빠른가"가 뒤집혔던 이유가 이것이다.
2. **커버리지 차이는 실재한다.** 1,258 ± 161 대 887 ± 25 로 두 구간이 겹치지
   않는다(최소 1,123 대 최대 910). LogosFuzz 표준편차는 25 에 불과하다.
   **자동 생성 하네스가 사람이 쓴 드라이버보다 약 30% 적게 커버한다.**
3. **버그 발현은 완전히 동일하다.** 6회 전부 PNG003, PNG006 이다.

### 3.3 1차 측정의 "PNG005 발견"은 재현되지 않았다

1차 비교에서 LogosFuzz 가 베이스라인이 못 건드린 PNG005 를 발현시켰고, 그때
리포트에 "각 1회라 우열을 말할 수 없고 PNG005 는 운일 수 있다"고 단서를 달았다.

**반복 6회에서 한 번도 재현되지 않았다. 운이었다.** 반복 측정을 하지 않았다면
없는 강점이 리포트에 남았을 것이다.

### 3.4 커버리지가 낮은 이유 — 확인된 원인과 개선 시도

두 하네스가 호출하는 API 를 비교하면 답이 나온다.

```
베이스라인(23개): ... png_set_expand, png_set_gray_to_rgb, png_set_scale_16,
                  png_set_packing, png_set_interlace_handling, png_read_update_info,
                  png_read_row, png_sig_cmp
LogosFuzz 1차(15개): create -> set_read_fn -> read_info -> get_IHDR -> read_image -> read_end
```

베이스라인은 **변환 설정 API 를 의도적으로 켠다.** 하나하나가 libpng 디코딩
코드의 큰 덩어리를 연다. 자동 생성 하네스는 기본 읽기 경로만 걸었다.

지식베이스는 API 목록과 시그니처를 알지만 "이 setter 가 코드 경로를 여는
스위치"라는 것은 모른다. 그래서 KB 가 이미 아는 사실 두 가지(같은 상태 핸들을
첫 인자로 받는가 / 공개 헤더에 선언됐는가)로 후보를 좁혀 GEN 프롬프트에 넣었다
(`kb_adapters.configuration_apis`). libpng 에서 후보 60개, OSS-Fuzz 가 켜는 7개를
**7/7 회수**, 내부 헬퍼 0개.

**주입은 의도대로 작동했다.** 새 하네스가 실제로 켠다.

```
1차: png_set_read_fn, png_set_sig_bytes
2차: + png_set_expand, png_set_gray_to_rgb, png_set_palette_to_rgb,
       png_set_filler, png_set_bgr
```

커버리지도 823 → 905 로 올랐다. **그러나 베이스라인과의 격차는 메우지 못했다**
(887 ± 25 대 1,258 ± 161). 켜는 API 를 알려주는 것만으로는 부족하고, 어떤 조합을
언제 켜야 깊은 경로가 열리는지까지는 아직 GEN 이 모른다.

### 3.5 GEN 시행착오 — 세 번의 실패가 무엇을 가르쳤나

| 시도 | 프롬프트에 준 것 | 결과 |
| --- | --- | --- |
| 1 | 대상 API 9개 시그니처(KB) | **없는 함수를 지어냄** (`png_set_io_ptr`) |
| 2 | + 공개 API **이름** 216개 | 지어내기 사라짐. **인자 개수 오류** |
| 3 | + 공개 API **정본 프로토타입** 216개 | 여전히 인자 개수 오류, 5라운드 실패 |
| 4 | 3번과 동일 + **gpt-4o** | **1라운드 컴파일 성공** |

3번이 특히 중요하다. 정확한 프로토타입을 줬는데도 `png_destroy_read_struct` 를
한 곳은 3인자로 옳게, 두 곳은 2인자로 틀리게 썼고 자가 치유 5라운드가 이 사소한
반복 실수를 못 닫았다. **GEN 의 병목은 프롬프트가 아니라 모델이다.**

부수 발견: **EXT 가 `png_create_read_struct` 를 아예 놓쳤다.** libpng 은 공개
API 를 `PNG_EXPORT` 매크로로 선언하는데 EXT 의 시그니처 추출이 이 형태를 못
잡는다.

## 4. 4단계 — dlt-daemon 파싱 모듈

### 4.1 EXT / SCH

| 지표 | can-utils (3단계) | dlt 파싱 모듈 |
| --- | --- | --- |
| API | 675 | 190 |
| 제약조건 커버리지 | 32.15% | **85.19%** |
| 로직 그룹 | 83 | 15 |

`dlt_common.c` 는 cmake 생성 헤더 두 개에 의존한다. 치환자가 몇 개뿐이라 직접
생성했고, 링크에 `dlt_log.c`·`dlt_multiple_files.c` 가 추가로 필요하다.
결과적으로 ASAN + libFuzzer 로 단독 빌드된다.

### 4.2 GEN — 컴파일 성공률 2/5 (gpt-4o-mini)

드러난 GEN 결함 4건:

1. **LLM 이 헤더를 include 하고도 대상 함수를 다시 선언한다** → §1.7(b)
2. **C++ 대상을 C 로 컴파일한다** → §1.7(c)
3. **`static` 함수가 퍼징 대상이 된다.** 소스를 어떻게 고쳐도 사라지지 않는
   실패라 자가 치유가 라운드만 소진한다 → §1 표의 6번
4. **API 마다 선언 헤더가 다른데 하나로 고정하면 안 된다.** KB 는 이미
   `document["header"]` 로 알고 있다.

### 4.3 EXE / ANA

컴파일된 두 그룹 모두 수초 내에 하네스 자체 결함으로 종료했다.

- `lg_dlt_common`: 226회 실행 후 ASAN stack-buffer-overflow @ `dlt_set_id_v2`.
  이 함수는 `len` 과 무관하게 항상 `memset(id, 0, DLT_V2_ID_SIZE=255)` 하는데
  하네스가 4바이트 버퍼를 넘겼다. in-tree 호출부는 전부 255바이트를 할당하므로
  **하네스 계약 위반 = 오탐**이다. **ANA-05-01 은 이것을 정탐(0.9)으로
  분류했다**(§2.4).
- `lg_DltMessageV2`: ASAN 리포트 없이 SIGSEGV. 종료 코드를 함께 보지 않으면
  크래시가 조용히 사라진다.

## 5. 4단계 확장 — Eclipse S-CORE

### 5.1 대상 선정

S-CORE(`github.com/eclipse-score`)의 C++ 저장소 중 `logging` 을 골랐다.
`score/mw/log/detail/common/dlt_format.cpp` 는 DLT 페이로드 직렬화기로, 팀이
계속 다뤄 온 프로토콜과 같고 바이트 버퍼를 받는 오버로드가 있어 퍼징 대상이 된다.

### 5.2 빌드 제약을 뚫는 과정

S-CORE 는 Bazel 모듈 시스템을 쓴다. 두 단계가 필요했다.

| 막힌 것 | 원인 | 해결 |
| --- | --- | --- |
| `add_argument_result.h` 없음 | `@score_baselibs` 모듈 의존 | `eclipse-score/baselibs` 클론 후 include 추가 |
| `visit_as_struct.h` 없음 | 실제 경로 `visitor/include/visitor/…` 를 `static_reflection_with_serialization/visitor/…` 로 include | Bazel `include_prefix`/`strip_include_prefix` 를 파일 복사로 재현 |

**결과: Bazel 없이 컴파일·링크된다.** S-CORE 모듈을 파이프라인에 붙일 수 있다.

### 5.3 파이프라인 실행 결과

| 단계 | 결과 |
| --- | --- |
| EXT | API 388 / 헤더 136 / 제약조건 커버리지 **16.75%** |
| SCH | 111그룹, **최대 32(상한), 전부 32 이하** — 그룹 폭발 수정이 C++ 에서도 유지 |
| GEN | **0라운드 컴파일 성공** (gpt-4o, 언어 판별 `cpp` 정상 동작) |
| EXE | 300초 / **141,551,960 실행** / 470,272 exec/s / 커버리지 32 |
| ANA | 크래시 없음 |

**커버리지 32 는 낮다.** 직렬화기가 작기도 하지만 하네스가 몇 개 오버로드만
태웠을 가능성이 크다. "S-CORE 에서 파이프라인이 돈다"는 확인이지 "충분히
테스트했다"는 뜻이 아니다.

**새 결함**: API 388개 중 **187개(48.2%)가 테스트 코드**였고 SCH 가 그걸 최우선
그룹으로 올렸다 → §1.8 에서 수정.

## 6. 측정 자체의 신뢰성 — 내가 만든 오류 3건

이번 검증에서 **측정 장치가 측정 대상을 망가뜨린 경우가 세 번** 있었다. 전부
같은 부류이므로 함께 기록한다.

| # | 무엇 | 증상 | 발견 경위 |
| --- | --- | --- | --- |
| 1 | Dockerfile ENTRYPOINT 이중 적용 | 컨테이너 안에서 아무것도 실행 안 됨, exit 0 | 1단계 검증 |
| 2 | libFuzzer `-close_fd_mask=1` | ASAN 리포트까지 차단, SIGSEGV 가 "크래시 0건"으로 집계 | 4단계 측정 중 |
| 3 | 캠페인 로그를 Windows 바인드 마운트에 기록 | 로그 I/O 가 퍼저를 throttle, 같은 바이너리가 5,704 → 1,072 exec/s | 2단계 측정 중 |
| 4 | 메모리 상한 없이 캠페인 실행 | 가용 2GB 인데 LogosFuzz 하네스 피크가 2.4GB → 한쪽만 스왑에 걸려 비대칭으로 느려짐 | 2단계 반복 측정 준비 중 |

3번은 **비교 순위를 뒤집었다.** 퍼징 수치를 낼 때는 로그 처리 경로와 메모리
여유가 측정에 개입하지 않는지 먼저 확인해야 한다.

여기에 더해, 반복 측정 중 `baseline_r2` 캠페인 하나가 2초 만에 출력 없이 종료해
실패했다. 그대로 평균을 내면 베이스라인 커버리지가 779 ± 676 으로 나온다(실패
회차의 0 이 섞인다). **실패한 회차를 조용히 빼거나 그대로 평균 내지 않고
재실행했다.** 재실행은 정상 동작했다(execs 5,857,508 / cov 1437).
