# 검증 2단계·4단계 — 성능 비교 / dlt-daemon 모듈 확장

> 대상 저장소: `origin/dev` 기준 브랜치 `validation/step2-step4`
> 환경: Windows 11 + Docker Desktop 28.5.1(`logosfuzz-exec` 이미지, clang-14 +
> libFuzzer + ASAN), Python 3.12, OpenAI `gpt-4o-mini`
> 최종 테스트: **366 passed**

앞선 1단계·3단계 검증 리포트의 §5 결론이 "2단계로 넘어가기 전에 격리 실행 버그와
ANA 판별 정확도부터 고치라"였다. 이 문서는 그 선행 수정과, 그 위에서 수행한
2단계(기존 방식 대비 정량 비교)·4단계(dlt-daemon 모듈 확장)의 기록이다.

## 0. 한 줄 요약

- 선행 수정 5건을 커밋했다. 그중 **ANA-05-01 정탐/오탐 판별은 정답 20건 기준
  10% → 85%** 로 올랐다.
- **1단계 리포트의 정답셋이 틀렸다는 것을 발견해 정정했다.** 오탐으로 알고 있던
  2건이 실제로는 정탐이었다.
- 2단계에서 **지식베이스 제약조건을 하네스에 반영하는 것만으로 동일 시간 실행량이
  15만 배 차이난다**는 것을 단일 변수 비교로 측정했다.
- 4단계는 `dlt_common.c` 파싱 모듈을 격리해 EXT→SCH→GEN→EXE→ANA 를 완주시켰다.
  다만 **하네스 컴파일 성공률 2/5, 생성된 하네스는 전부 수초 내 자기 자신의
  결함으로 종료**한다. 실제 취약점 탐지 단계에는 아직 이르지 못했다.

### 1.1 격리 실행 버그 — 실증

수정 전 형태와 수정 후 형태를 같은 이미지에서 직접 재현했다.

```
$ docker run --rm --entrypoint bash nginx:stable -lc bash -lc "echo SHOULD_NOT_PRINT"
(출력 없음)
exit=0        ← 명령이 실행되지 않았는데 성공으로 보인다

$ docker run --rm nginx:stable bash -lc "echo PRINTED_CORRECTLY"
PRINTED_CORRECTLY
exit=0
```

수정된 이미지로 실제 퍼징이 도는 것까지 확인했다 — dlt 파싱 모듈 하네스가
컨테이너 안에서 **4,545,355회 실행 / 37,564 exec/s** 로 동작한다(§2).

## 2. ANA-05-01 정탐/오탐 판별 재검증

### 2.1 정답셋을 바꾼 이유 — 1단계 리포트의 오류 정정

1단계 검증에서는 노션 문서를 근거로 `dlt_filter_delete_v2` 크래시
(`id_000001`, `id_000188`)를 **오탐**으로 놓고 5건을 측정했다.

같은 크래시를 더 깊이 분석한 4팀 크래시 분석 보고서는 이 둘을 **정탐**으로
판정한다. 근거가 명확하다.

- `dlt_filter_add_v2` 가 `apid2len` 을 캡핑하지 않고 저장하는데,
  `dlt_filter_delete_v2` 의 `memcmp` 가 그 길이를 **호출자 버퍼에도** 적용한다.
- 공개 API 계약을 하나도 어기지 않는 **정상 호출 2줄로 재현**된다.
- CWE-125.

그 보고서는 "in-tree 호출부가 0건"이라는 사실도 확인했지만, 그것이 도달 불가를
뜻하지 않는다고 명시한다 — 의도된 호출자가 libdlt 를 링크하는 서드파티
애플리케이션이기 때문이다. 이 지적은 이번 작업에서 추가한 신호 하나와 정면으로 배치되어, 해당 신호를
폐기했다(§2.3).

정정된 정답으로 다시 채점하면 1단계의 "60%" 는 성립하지 않는다. 같은 보고서가
근거와 함께 판정한 **20건(정탐 2 / 오탐 18)** 으로 정답셋을 교체했다. 표본이 4배
크고, 오탐이 압도적으로 많아 "오탐을 잡아내는가"를 재기에 적합하다.

### 2.2 무엇을 바꿨나

`logosfuzz/analyze/reachability.py`(신규)가 판정 대신 **증거**를 모은다.

| 증거 | 무엇을 판단하는 데 쓰나 |
| --- | --- |
| 크래시 함수의 정의·링키지·결함 라인 주변 소스 | 무엇을 인덱싱하다 터졌는가 |
| 호출부를 프로덕션 / 하네스·테스트로 분리 | 제품 경로에서 도달하는가 |
| 크래시를 낸 하네스 소스 | 하네스가 계약을 어겼는가 |
| **결함 라인이 읽은 필드를 쓰는 상태 기록 API 의 본문** | 계약을 지킨 경로로도 그 값이 나오는가 |

마지막 항목이 판정을 가른다. "하네스가 계약을 어겼다"는 오탐의 **충분조건이 아니다**.
계약을 어긴 하네스가 찾아낸 버그라도 계약을 지킨 호출로 같은 값이 만들어지면
진짜 결함이다 — `dlt_filter_delete_v2` 가 정확히 그 경우다. 그 판단을 하려면
값을 저장하는 쪽(`dlt_filter_add_v2`)의 소스가 필요하다.

### 2.3 규칙 기반이 할 수 있는 것과 없는 것을 분리했다

"이 인자 조합이 공개 API 로 도달 가능한가"는 불변식 추론이라 정규식으로 결론 낼
수 없다. 그래서 규칙 기반 판별기에 주는 신호는 **정적으로 증명 가능한 것만**이다.

- `harness-only-caller` — 헤더에 없고 하네스/테스트만 호출 → 오탐 쪽으로 민다
- `unreferenced-internal-function` — 헤더에도 없고 아무도 안 부름
- `public-api-no-in-tree-caller` — **점수를 깎지 않는다.** 공개 API 는 의도된
  호출자가 트리 밖이므로 "호출부 없음"이 오탐 근거가 될 수 없다.

세 번째 항목이 §2.1 의 지적을 반영한 결과다. 처음에는 "in-tree 호출부 0곳"에
감점을 줬고, 그 결과 `dlt_filter_delete_v2` 의 실제 결함이 오탐으로 분류됐다.

### 2.4 측정 결과 (정답 20건, gpt-4o-mini, 3회 반복)

| 구성 | 정확도 | 정탐 재현율 | 오탐 재현율 | 오탐→정탐 오분류 |
| --- | --- | --- | --- | --- |
| `rule_plain` (개선 전) | 2/20 (10%) | 2/2 | 0/18 | 9건 |
| `rule_ctx` (규칙 + 도달가능성 신호) | 2/20 (10%) | 2/2 | 0/18 | 9건 |
| `llm_baseline` (1단계 당시 프롬프트) | 2/20 (10%) | 2/2 | 0/18 | 18건 |
| **`llm_ctx` (새 프롬프트 + 증거)** | **17/20 (85%)** | 1/2 | **16/18** | **1건** |

3회 반복에서 **판정이 갈린 케이스 0건** — 85%는 잡음이 아니다.

읽는 법:

- 규칙 기반은 오탐을 하나도 잡지 못한다(0/18). 도달 가능성 신호를 붙여도
  그대로다. 이 20건은 전부 제품 코드가 호출하는 공개 API 에서 났기 때문에,
  정적으로 증명 가능한 신호가 발화하지 않는다. 규칙 기반의 한계는 프롬프트가
  아니라 **판정에 불변식 추론이 필요하다**는 사실 자체다.
- 개선의 대부분은 증거 주입에서 나온다. 같은 모델·같은 온도인데 10% 에서 85% 로
  올랐다.
- 남은 오류 1건(`id_000188`)은 `id_000001` 과 근본 원인·수집 증거가 동일한데도
  판정이 갈린다. 근거문에 "계약을 지켰다"고 쓰면서 오탐으로 결론짓는 모순을
  보인다. 프롬프트가 아니라 gpt-4o-mini 의 추론 한계이며, 설계서가
  지정한 추론형 모델(DeepSeek-R1)로 바꿀 근거다.

### 2.5 한계

이 수치는 일반화되지 않는다. 4단계에서 새로 나온 크래시(§4.4)에 같은 판별기를 걸었더니
하네스가 만든 크래시를 정탐(0.9)으로 분류했다. 20건은 전부 같은 캠페인·같은
대상에서 나왔고, 그중 18건이 소수의 오탐 패턴(NULL 인자, 셋업 단계 크래시)에
몰려 있다. 다른 대상·다른 패턴에서 같은 수치가 나올 것으로 기대하면 안 된다.

## 3. SCH-02-01 / GEN-03-03 — 3단계에서 남긴 숙제

### 3.1 그룹 폭발 (can-utils, API 675개)

호출 엣지를 무조건 이어서 전이적 병합으로 API 의 **90%(609/675)** 가 상태 타입
하나 밑으로 전부 빨려 들어갔다. 그룹은 GEN 이 하네스 하나를 만드는 단위라, 이
크기면 하네스가 라이브러리 전체를 상대해야 해서 퍼징 단위로 쓸 수 없다.

두 가지를 고쳤다.

1. **그룹 양쪽이 이미 상태 타입을 가지면 잇지 않는다.** 이 판정은 개별 API 가
   아니라 **그룹 단위**로 해야 한다 — API 두 개만 비교하면, 타입 없는 유틸 하나가
   A 머신에 흡수된 뒤 B 머신도 그 유틸을 부르는 순간 유틸을 다리 삼아 A 와 B 가
   합쳐진다. 609개짜리 그룹이 정확히 이렇게 생겼다.
2. **`MAX_CALL_LINK_GROUP`(기본 32, `--max-call-group`)** 상한.

| | 그룹 수 | 최대 그룹 | state_type 기반 |
| --- | --- | --- | --- |
| 수정 전 | 35 | **609 (90%)** | 2 |
| 수정 후 | 83 | **157 (23%)** | 19 |

83개 중 77개가 32개 이하다. 남은 157/103 짜리는 `isobusfs`·`j1939` 처럼 실제로 한
핸들 타입을 공유하는 서브시스템이라 호출 관계 문제가 아니다.

### 3.2 LIBC_ALLOWLIST 공백

실제 SocketCAN 유틸 `isotpsend.c` 에서 `socket`/`bind`/`setsockopt`/`close`/
`write`/`if_nametoindex` 가 전부 모킹 후보로 잡혔다. 가짜 stub 이 함께
컴파일되면 링크가 깨지거나, 진짜 소켓 호출이 stub 으로 조용히 대체되어 대상이
아무 통신도 안 하면서 정상으로 보인다.

허용목록을 24 → 236개로 넓혔다(stdio/string/stdlib/ctype/POSIX IO/소켓·네트워크/
시간/프로세스·시그널·스레드). 3단계에서 잘못 잡힌 14개가 전부 걸러지고, 진짜
프로토콜 API(`isotp_send` 등)는 그대로 후보로 남는다. 연산자인 `sizeof` 가 모킹
후보로 올라오던 것도 막았다.

## 4. 4단계 — dlt-daemon 파싱 모듈 격리

테스트 계획의 "추가 제안"대로 daemon 전체가 아니라 `dlt_common.c` 파싱 모듈만
떼어냈다.

### 4.1 모듈을 빌드 가능하게 만들기

`dlt_common.c` 는 cmake 가 생성하는 헤더 두 개(`dlt_user.h`, `dlt_version.h`)에
의존한다. 치환자가 몇 개뿐이라 직접 생성했다(네트워크 트레이스 ON,
`DLT_DISABLE_MACRO 0`, v3.0.1 STABLE). 링크에는 `dlt_log.c`,
`dlt_multiple_files.c` 가 추가로 필요하다.

결과: **`dlt_common.c` + 의존 2개가 ASAN + libFuzzer 로 단독 빌드된다.**

### 4.2 EXT / SCH

| 지표 | can-utils (3단계) | dlt 파싱 모듈 (4단계) |
| --- | --- | --- |
| API | 675 | 190 |
| 제약조건 커버리지 | 32.15% | **85.19%** |
| 로직 그룹 | 83 | 15 |
| 최대 그룹 | 157 | 62 |

문서 주석이 잘 붙어 있는 모듈이라 제약조건 커버리지가 훨씬 높다.

### 4.3 GEN — 하네스 컴파일 성공률 2/5

| 그룹 | 결과 | 원인 |
| --- | --- | --- |
| `lg_dlt_common` | **성공 (초안 그대로)** | — |
| `lg_DltMessageV2` | **성공 (초안 그대로)** | — |
| `lg_dlt_cpp_extension` | 실패 (4라운드 소진) | `dlt_init_context` 등 미선언 |
| `lg_dlt_cpp_extension_2` | 실패 (2라운드 정체) | `'delete' is a keyword` |
| `lg_DltTraceLoadSettings` | 실패 (4라운드 소진) | 타입 미선언 → 링크 에러 |

진행 중 드러난 GEN 결함:

1. **LLM 이 헤더를 include 하고도 대상 함수를 다시 선언한다.** 그 선언이 헤더와
   `const` 하나만 달라도 `conflicting types` 로 깨지고, 자가 치유는 같은 에러를
   반복하다 정체된다. 프롬프트로 금지해도 계속 재발해, 후처리로 결정적으로
   제거해야 했다. 초안뿐 아니라 수정 라운드의 응답에도 적용해야 한다(초안에만
   걸면 자가 치유가 되살린다).
2. **C++ 대상을 C 로 컴파일한다.** SCH 는 언어를 구분하지 않아 `dlt_cpp_extension.hpp`
   의 `logToDlt` 가 C 그룹과 나란히 나온다. C 로 컴파일하면 `'map' file not found`
   처럼 원인과 동떨어진 에러가 뜨고 자가 치유가 엉뚱한 곳을 고친다.
3. **`static` 함수가 퍼징 대상이 된다.** `dlt_print_hex_string_delim` 이 그랬다.
   별도 컴파일 단위인 하네스는 내부 링키지 함수를 링크할 수 없고, 이건 **소스를
   어떻게 고쳐도 사라지지 않는 실패**라 자가 치유가 라운드만 소진한다. 대상 선정
   단계에서 걸러야 한다 → `src/knowledge_base.py` 가 `is_static` 을 기록하도록
   고쳤다(190개 중 11개가 static).
4. **API 마다 선언 헤더가 다른데 하나로 고정하면 안 된다.** KB 는 이미
   `document["header"]` 로 알고 있다.

### 4.4 EXE / ANA — 완주하지만 실제 취약점에는 못 미친다

컴파일에 성공한 두 그룹 모두 **수초 내에 자기 자신의 결함으로 종료**했다.

- `lg_dlt_common`: 226회 실행 후 ASAN `stack-buffer-overflow` @ `dlt_set_id_v2`.
  `dlt_set_id_v2` 는 `len` 과 무관하게 항상 `memset(id, 0, DLT_V2_ID_SIZE=255)`
  를 하는데 하네스가 4바이트 버퍼를 넘겼다. in-tree 호출부(`dlt_filter_add_v2`)는
  전부 255바이트를 할당하므로 **하네스 계약 위반 = 오탐**이다.
  → **ANA-05-01 은 이것을 정탐(0.9)으로 오판했다**(§2.5).
- `lg_DltMessageV2`: ASAN 리포트 없이 SIGSEGV(rc 139). ANA 는 파싱할 리포트가
  없어 **결함 0건**으로 본다. 종료 코드를 함께 보지 않으면 크래시가 조용히
  사라진다.

## 5. 2단계 — 정량 비교

### 5.1 왜 Magma/FuzzBench 를 그대로 쓰지 않았나

FuzzBench 는 구글 클라우드 규모 인프라를 전제하고, Magma 는 타겟당 수 시간짜리
캠페인을 요구한다. 그보다 먼저, **§4.4 대로 생성된 하네스가 수초 만에 자기
결함으로 죽는 상태에서는 어떤 커버리지 비교도 하네스 품질을 재는 것이지 퍼징
성능을 재는 게 아니다.** 1단계 리포트가 "먼저 고치고 재검증하라"고 한 이유다.

대신 **파이프라인의 핵심 주장 하나를 단일 변수로 분리해서** 쟀다: 지식베이스가
뽑은 제약조건을 하네스에 반영하면 실제로 이득이 있는가.

### 5.2 측정 설계

같은 대상(`dlt_print_hex_string`), 같은 컴파일 옵션, 같은 시간(120초), 같은
libFuzzer 설정. **다른 것은 길이 인자 하나뿐이다.**

- **A (제약조건 준수)**: `size` = 실제 버퍼 길이, `textlength` = 실제 출력 버퍼 크기
- **B (제약조건 무시)**: 두 길이를 퍼징 입력에서 각각 독립적으로 뽑는다

KB 가 이 API 에 대해 뽑아 둔 제약조건이 근거다:
`"'size' describes the length of buffer 'ptr'; the harness must keep them consistent"`

### 5.3 결과

| | 120초 실행 | exec/s | 커버리지 | 종료 |
| --- | --- | --- | --- | --- |
| **A — 제약조건 준수** | **4,545,355** | 37,564 | cov 14 / ft 30 / corp 10 | 정상 완주, 크래시 0 |
| **B — 제약조건 무시** | **30** | 0 | cov 10 / ft 11 / corp 2 | **30회 만에 하네스 자체 크래시** |

`heap-buffer-overflow @ dlt_common.c:180 in dlt_print_hex_string_delim` — B 의
크래시는 대상 결함이 아니라 버퍼보다 큰 `size` 를 넘긴 하네스 잘못이다.

**같은 시간에 실행량이 15만 배 차이난다.** 제약조건을 무시한 하네스는 대상 코드를
탐색하기 전에 자기 자신이 죽어서 퍼징이 성립하지 않는다. EXT 단계의 제약조건
추출이 실제로 값을 만든다는 것을 이 대상에서 정량으로 확인했다.

### 5.4 이 수치의 한계

- **대상 1개, API 1개, 캠페인 1회다.** 반복 실행이나 다른 타겟으로 확장하지
  않았으므로 분산을 모른다.
- **기존 퍼저(AFL++/libFuzzer 단독) 대비 비교가 아니다.** 같은 퍼저(libFuzzer)로
  하네스 품질만 비교한 것이다. 개발보고서의 "기존 퍼저 대비 성능 비교" 항목을
  채우려면 별도 실험이 필요하다.
- 참고로 팀이 이전에 수행한 AFLNet 캠페인은 같은 dlt-daemon 대상에서 56분에
  201 paths / 18,347 execs / 크래시 0 이었다. 계측 방식·대상 범위·측정 환경이
  달라 위 표와 직접 비교할 수 없다.

## 6. 다음에 해야 할 것

1. **하네스 컴파일에 포인터 타입 경고를 에러로 올려라.**
   현재 파이프라인은 `returncode == 0` 이고 로그에 `error:` 가 없으면 성공으로
   본다. `char *` 를 `char **` 자리에 넘기는 것은 C 에서 **경고**라 빌드가
   "성공"하고 하네스는 첫 입력에서 죽는다. 실제로 이번 비교 하네스가 그렇게
   깨졌고, `-Werror=incompatible-pointer-types` 를 걸자 즉시 잡혔다.
   "컴파일 성공률 100%" 가 의미를 가지려면 이 게이트가 필요하다.
2. **`static`/C++ 여부를 SCH 단계에서 대상 선정에 반영하라.** KB 는 이제
   `is_static` 을 기록한다. 언어 판별도 같은 자리에서 해야 한다.
3. **자가 치유가 못 고치는 실패를 구분하라.** 링크 에러(내부 링키지)와 타입
   미선언은 소스 수정으로 사라지지 않는다. 라운드를 소진하는 대신 조기에
   대상 선정으로 되돌려야 한다.
4. **ANA-05-01 을 추론형 모델로 교체하고 다른 대상에서 재측정하라.** 85%는
   같은 캠페인 20건 기준이고, 새 크래시에서는 오판했다.
5. GEN-03-01 이 두 갈래(`logosfuzz/generate/` vs 루트
   `gen_03_01_harness_generator.py`)로 나뉜 채라, 이번 4단계는 어느 쪽도 그대로
   쓰지 못하고 별도 러너로 구동했다. 통합이 남아 있다.
