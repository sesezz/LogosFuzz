# EXT-01-02 RAG 제약조건 추출

C/C++ 소스에서 **API 제약조건**을 추출하고, 하네스 생성기(GEN-03-01)가 질의할 수 있는
**RAG 지식베이스**로 색인한다.

`EXT-01-01 AST 분석`이 파일 단위 구조를 본다면, 이 모듈은 함수 단위로
"이 API를 호출하려면 무엇이 참이어야 하는가"에 답한다.

## 파이프라인

```
compile_commands.json (EXT-01-03)  ─┐
                                    ├─▶ constraint_extractor ─▶ 함수별 제약조건
경로 목록 (--paths)                ─┘                              │
                                                                   ▼
                        GEN-03-01 프롬프트 컨텍스트 ◀── rag_index (BM25 검색)
```

| 파일 | 역할 |
| --- | --- |
| [logosfuzz/extract/constraint_extractor.py](../logosfuzz/extract/constraint_extractor.py) | 소스 파싱 + 제약조건 규칙 |
| [logosfuzz/knowledge/rag_index.py](../logosfuzz/knowledge/rag_index.py) | BM25 색인 / 저장·로드 / (선택) 밀집 검색 |
| [logosfuzz/knowledge/rag_constraints.py](../logosfuzz/knowledge/rag_constraints.py) | 지식베이스 구축·검색 CLI |

## 추출하는 제약조건

| kind | 근거 | 하네스 생성 시 의미 |
| --- | --- | --- |
| `assert` | `assert(...)`, `BUG_ON(...)` | 명시된 사전조건 (신뢰도 0.95) |
| `null_check` | `if (!p)` + 거부 경로 | 해당 포인터에 NULL을 넣으면 안 됨 |
| `nullable` | `if (p != NULL)` 방어, 또는 NULL을 처리하고 계속 진행 | NULL을 넣어도 되는 인자 |
| `buffer_size` | `(T *buf, size_t len)` 인자 쌍 | 버퍼와 길이를 일치시켜야 함 |
| `range_check` | `if (n <= 0) return -1;` | 숫자 인자의 유효 범위 |
| `resource` | `malloc`/`fopen`/`open` 등 | 해제 책임이 호출자에게 있는지 |
| `return_value` | `return NULL;` / `return -1;` | 실패 시 반환값 규약 |
| `risky_call` | `memcpy`, `strcpy`, `alloca` … | 길이 검증이 필요한 지점 (퍼징 표적) |
| `doc` | `@param`, "must not be NULL" | 주석에 서술된 제약조건 |

### 분기 분류가 핵심이다

비교 연산자를 뒤집어 **호출자가 만족시켜야 하는 조건**으로 바꾸는 것은
분기가 *입력을 거부하는 경로*일 때만 옳다. 그래서 `if` 본문을 정확히 잘라내
세 가지로 분류한다.

| 분류 | 판단 근거 | 처리 |
| --- | --- | --- |
| `error_exit` | `return -1` / `return NULL` / `goto ...fail` / `abort()`·`*FatalError()` | 부등호를 뒤집어 요구조건으로 기록 (conf 0.8~0.9) |
| `plain_exit` | 그 밖의 `return`·`break` | 뒤집지 않음 (conf 0.6) |
| `none` | 분기 안에서 빠져나가지 않음 | 뒤집지 않고 **경계값 힌트**로 기록 (conf 0.4) |

```c
if (n <= 0) { return -1; }          // → "n > 0 이어야 한다"       (요구조건)
if (x != 0) { return compute(x); }  // → "0은 경계값"              (요구조건 아님!)
if (p == NULL) { p = &fallback; }   // → nullable (NULL 허용)      (금지 아님!)
```

두 번째·세 번째를 요구조건으로 기록하면 **정반대 결론**이 나온다. 실제
CPython 헤더 214개로 검증하면서 잡아낸 오류이며, 회귀 테스트로 고정해 두었다.

### 반복 제약조건 병합

생성된 코드는 같은 `assert`를 수천 번 반복하기도 한다(CPython의
`_PyUnicode_InitStaticStrings`는 1406개). 동일한 제약조건은 하나로 합치고
`occurrences`에 횟수를 기록한다. 이 함수의 경우 문서 크기가 145 KB → 571 B로
줄어든다. 병합하지 않으면 문서 하나가 색인 전체의 단어 빈도를 왜곡한다.

## 사용법

### 1. 지식베이스 구축

```bash
# 디렉터리에서
python -m logosfuzz.knowledge.rag_constraints build --paths examples --output build/kb.json

# compile_commands.json(EXT-01-03 결과)에서
python -m logosfuzz.knowledge.rag_constraints build --compile-db build/compile_commands.json \
    --output build/kb.json
```

출력:

```json
{
  "output": "build/kb.json",
  "functions": 7,
  "files": 2,
  "constraints": 18,
  "by_kind": { "assert": 1, "null_check": 3, "buffer_size": 1, "...": 0 },
  "coverage": 0.4286,
  "dense_backend": false
}
```

`coverage`는 **제약조건이 하나 이상 추출된 함수의 비율**이다. 6주차 "API 추출 정확도 평가"의
기준선으로 쓸 수 있다.

### 2. 검색

```bash
python -m logosfuzz.knowledge.rag_constraints query --kb build/kb.json "버퍼 길이 제약" --top-k 3
python -m logosfuzz.knowledge.rag_constraints query --kb build/kb.json "who must free the result"
```

한국어 질의는 소규모 동의어 사전으로 확장된다(`버퍼`→`buffer`, `해제`→`free` …).

### 3. 하네스 생성용 컨텍스트 (GEN-03-01 연동 지점)

```bash
python -m logosfuzz.knowledge.rag_constraints context --kb build/kb.json --function parse_header
```

```
## parse_header  (examples/parser_sample.c:26)
signature: int parse_header(const char *buf, size_t len, struct header *out)
doc: 입력 버퍼에서 헤더 하나를 파싱한다.
constraints:
  - (assert, conf=0.95) [len] precondition asserted in the body: len <= MAX_HEADER
      evidence: len <= MAX_HEADER
  - (null_check, conf=0.9) [buf] 'buf' must not be NULL when calling this function
      evidence: !buf || out == NULL
  - (buffer_size, conf=0.85) [buf,len] 'len' describes the length of buffer 'buf'; ...
```

이 블록을 그대로 LLM 프롬프트에 붙이면 된다. 파이썬에서는:

```python
from logosfuzz.knowledge.rag_constraints import ConstraintKB

kb = ConstraintKB.load("build/kb.json")
prompt_context = kb.context_for("parse_header")
constraints = kb.constraints_of("parse_header")   # 구조화된 dict 목록
hits = kb.search("길이 검증이 필요한 함수", top_k=5)
```

### 4. 통계

```bash
python -m logosfuzz.knowledge.rag_constraints stats --kb build/kb.json
```

## 설계 메모

- **의존성 없음.** BM25 검색기는 순수 파이썬이라 CI에서 그대로 돈다.
  `sentence-transformers`가 설치되어 있으면 `--dense` 옵션으로 밀집 검색을 켤 수 있고,
  두 결과는 RRF(reciprocal rank fusion)로 합쳐진다. 설치되어 있지 않으면 BM25만 쓴다
  (`logosfuzz/extract/ast_analyzer.py`가 clang을 선택적으로 쓰는 것과 같은 방식).
- **토크나이저가 코드를 안다.** `parse_http_header`는 `parse`/`http`/`header`로도
  색인되므로 `"header parsing"` 같은 질의가 걸린다.
- **주석/문자열/전처리기는 마스킹.** 오프셋을 보존한 채 공백으로 치환해서
  `char *s = "}"` 같은 코드가 파서를 깨뜨리지 않는다. 사람이 읽을 근거(`evidence`)는
  원본에서 잘라낸다.
- **clang이 없어도 동작한다.** 규칙은 정규식과 괄호 매칭 기반이므로 헤더를 모두
  갖추지 못한 프로젝트에서도 부분 결과를 얻을 수 있다.

## 실제 코드 검증

CPython 3.12 헤더 **214개**(내부 헤더 포함)로 검증했다.

| 항목 | 결과 |
| --- | --- |
| 파싱 실패/예외 | 0건 |
| 함수 정의 탐지 | 276개 탐지 = 실제 276개 (**오탐 0, 미탐 0**) |
| 처리 시간 | 214파일 약 1.9초 |
| 제약조건 | 167개 (중복 병합 후), 함수 커버리지 35.5% |

탐지된 276개는 `static inline` 268개, `inline` 5개, `static __inline__` 3개로
전부 실제 정의였다. 매크로·주석·문자열 마스킹 덕분에 헤더의 매크로 정의를
함수로 오인하지 않는다.

재현:

```bash
python -m logosfuzz.knowledge.rag_constraints build --paths <파이썬설치경로>/include --output build/kb_cpython.json
python -m logosfuzz.knowledge.rag_constraints query --kb build/kb_cpython.json "reference count increment"
# -> _Py_RefcntAdd
```

## 한계

- 매크로로 감싼 제약조건(`CHECK_ARG(p)` 같은 프로젝트 고유 매크로)은 `assert` 계열
  이름 목록에 없으면 놓친다. `ASSERT_RE`에 추가하면 된다.
- 함수 간 전파(호출자에서 검사하고 피호출자는 믿는 경우)는 추적하지 않는다.
  EXT-01-04 KB 통합에서 호출 그래프와 함께 다루는 것이 자연스럽다.
- C++ 템플릿/네임스페이스는 이름만 기록하며 오버로드를 구분하지 않는다.
