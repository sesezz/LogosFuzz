### 헤더 문서를 구현에 결합

C 프로젝트는 보통 `.h` 선언에 문서를 달고 `.c` 정의에는 달지 않는다. 파일별로
따로 보면 문서 기반 제약조건이 통째로 사라진다. 통합 단계에서 이어 붙인다.

```c
/* uds.h */
/** @param ctx 열린 컨텍스트. must not be NULL. */
int uds_session_start(uds_ctx_t *ctx, uint8_t level);

/* uds.c — 문서 주석 없음 */
int uds_session_start(uds_ctx_t *ctx, uint8_t level) { ... }
```

예제 기준 제약조건이 **19개 → 29개**로 늘어난다 (`doc` 0 → 10).

## B 지원

### SCH-02-02 / SCH-02-03 — 목업 데이터 교체

B의 파일은 건드리지 않는다. B가 이미 정의해 둔 `ApiMetadata`/`Constraint`를
그대로 만들어 준다.

```python
from src.knowledge_base import KnowledgeBase
from src.kb_adapters import to_synergy_inputs
from sch_02_02_synergy_scheduler import compute_pairwise_synergy, rank_logic_groups

kb = KnowledgeBase.load("build/kb.json")
apis, constraints = to_synergy_inputs(kb)      # 목업 하드코딩을 이 한 줄로 대체
results = compute_pairwise_synergy(apis, constraints)
```

실제 실행 결과 (examples/uds):

```
uds_open          <-> uds_close         : score=0.9   adjacency=1.0 coupling=1.0
uds_open          <-> uds_session_start : score=0.85  adjacency=1.0 coupling=0.5
uds_session_start <-> uds_read_did      : score=0.76  adjacency=1.0 coupling=0.2
uds_open          <-> uds_read_did      : score=0.275 adjacency=0.0
```

> **`call_seq` 형식 주의.** SCH-02-02의 `call_adjacency_score`는 시퀀스 안에서
> **자기 자신의 api_id**를 찾아 이웃을 센다. 그래서 `call_seq`는 "이 API가
> 호출하는 목록"이 아니라 **"이 API를 호출하는 코드에서 관찰된 호출 순서"**여야
> 한다. 전자를 넣으면 자기 id가 없어 인접도가 **항상 0**이 된다(가중치 0.5짜리
> 항목이 통째로 죽는다). 회귀 테스트 `test_call_adjacency_is_actually_scored`
> 로 고정해 두었다.

`source_type`은 기본적으로 `CODE:<파일>` / `DOC:<파일>`로 매긴다. 규격서(UDS/CAN)
기반 제약이 들어오면 규격명을 쓰도록 바꿀 수 있다.

```python
apis, constraints = to_synergy_inputs(kb, source_type=lambda c, d: "UDS_SPEC")
apis, constraints = to_synergy_inputs(kb, min_confidence=0.85)   # 약한 제약 제외
```

## D 지원

### GEN-03-02 — 컴파일 에러 자가치유

gcc/clang 출력을 파싱해 지식베이스에서 찾은 수정안을 돌려준다.

```python
from src.kb_adapters import suggest_fixes
fixes = suggest_fixes(kb, compiler_stderr)
```

| 인식하는 에러 | `action` | 제공 내용 |
| --- | --- | --- |
| implicit declaration / undeclared | `add_include` | `#include "uds.h"` + `-I` 플래그 |
| unknown type / incomplete type | `add_include` | 타입을 정의한 헤더 |
| too few/many arguments | `fix_call_signature` | 정확한 시그니처와 파라미터 목록 |
| undefined reference (정의 있음) | `link_source` | 정의가 있는 `.c` 파일 |
| undefined reference (선언만 있음) | `link_library` | 선언 위치 + 라이브러리 링크 안내 |
| file not found | `add_include_path` | 헤더 위치 / 기록된 `-I` 경로 |

> `#include "..."`는 **포함하는 파일 기준**으로 해석되므로, 헤더 이름만 쓰고
> 디렉터리는 `-I`로 넘겨야 하네스 위치와 무관하게 컴파일된다. 그래서 각 제안은
> `detail`(include 문)과 `compile_flag`(`-I...`)를 함께 준다.

**실제 gcc로 검증한 자가치유 루프** (MinGW gcc 16.1.0):

```
[round 1] 실패 · 수정안 6건 · 종류=['implicit_declaration', 'unknown_type']
        + #include "uds.h"
        + -Iexamples/uds
[round 2] 실패 · 수정안 1건 · 종류=['argument_count']
        시그니처: int uds_read_did(uds_ctx_t *ctx, uint16_t did, uds_response_t *out, size_t len)
[round 3] 컴파일 성공
```

## 한계

- `api_id`는 **같은 입력에 대해서만** 안정적이다. 소스가 바뀌어 함수가
  추가/삭제되면 ID가 밀린다. 영속 저장이 필요하면 `(file, name)`을 키로 쓰고
  `api_id`는 실행 단위 조인 키로만 쓰는 것이 안전하다.
- 호출 그래프는 이름 기준이라 함수 포인터 호출과 오버로드는 추적하지 못한다.
- `header` 추정은 "같은 basename 우선, 없으면 최단 경로"라는 휴리스틱이다.
  같은 이름을 여러 헤더가 선언하면 틀릴 수 있다.
