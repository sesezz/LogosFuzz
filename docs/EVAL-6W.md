# 6주차 평가: KB Coverage / API 추출 정확도 / RAG 검색 성공률

`src/kb_eval.py` 하나로 세 지표를 함께 측정한다.

```bash
python -m src.kb_eval run --paths examples/uds --labels examples/uds/labels.json --report
python -m src.kb_eval run --paths <소스경로> -o build/eval.json
```

## 정답셋(ground truth)을 어디서 얻는가

정확도·성공률은 정답이 있어야 잴 수 있다. 세 경로를 순서대로 시도한다.

| 순위 | 방식 | 독립성 | 조건 |
| --- | --- | --- | --- |
| 1 | **clang** — libclang 으로 함수 정의 수집 | 높음 | `libclang.dll` 필요 |
| 2 | **nm** — 컴파일 후 심볼 테이블에서 정의 수집 | 높음 | gcc + nm, 대상이 컴파일돼야 함 |
| 3 | **labels** — 손으로 적은 JSON | 낮음(사람이 씀) | 라벨 파일 |

`--prefer clang|nm|labels` 로 고정할 수 있다. **어떤 경로를 썼는지와 폴백 사유는
결과의 `ground_truth.note` 에 남는다.** 수치만 보고 근거를 오해하지 않기 위해서다.

```
정답셋 : nm (6개) - gcc+nm, 컴파일 2건 (폴백 사유: libclang 바이너리 없음: ...)
```

`nm` 은 컴파일러/링커가 직접 알려주는 값이라 추출기와 독립적이다. 다만 심볼
이름만 주므로 인자 개수·반환형 비교는 불가능하다 — 그 항목은 0% 가 아니라
**미측정**으로 표시된다(분모에서 뺀다).

라벨 파일 형식은 [examples/uds/labels.json](../examples/uds/labels.json) 참고.

## 세 지표

### 1. API 추출 정확도

추출한 함수 집합을 정답과 대조해 precision / recall / F1 을 낸다. 이름이 맞은
항목에 한해 인자 개수·반환형까지 비교한다(정답셋이 그 정보를 가진 경우만).

오탐/미탐 함수 이름을 최대 20개까지 같이 내보내므로 원인 추적이 가능하다.

### 2. KB Coverage

정답 API 중 몇 개가 색인됐는지(`api_coverage`)와, 색인된 API 가 각 정보를
얼마나 갖췄는지를 함께 본다.

| 항목 | 의미 |
| --- | --- |
| `with_constraint` | 제약조건이 하나 이상 있는 비율 |
| `with_doc` | 문서 주석이 결합된 비율 |
| `with_header` | include 할 헤더가 해석된 비율 |
| `in_call_graph` | 호출 그래프에 편입된 비율 |
| `constraints_per_api` | API 당 제약조건 수 |

### 3. RAG 검색 성공률

`recall@1` / `recall@k` / `MRR` 을 잰다. 질의는 두 가지로 만든다.

- **자동(기본)**: 각 API 의 문서·제약조건 텍스트를 질의로 쓴다.
  **함수 이름과 그 부분 토큰은 질의에서 제거한다.** 이름이 남아 있으면
  식별자 완전일치로 걸려서 검색력이 아니라 이름 노출 여부를 재게 된다.
- **파일**: `--queries` 로 `[{"query": ..., "expect": 함수명}]` 지정.

실패한 질의의 정답 함수를 최대 10개까지 같이 내보낸다.

## 측정 결과 (examples/uds)

```
정답셋      : nm (6개) - gcc+nm, 컴파일 2건

[1] API 추출 정확도
  precision 1.000 / recall 1.000 / F1 1.000
  정탐 6 · 오탐 0 · 미탐 0

[2] KB Coverage
  대상 API 6개 중 색인 6개 (coverage 1.000)
  제약조건 보유 0.833 · 문서 보유 0.500 · 헤더 해석 0.667
  호출그래프 편입 1.000 · API당 제약조건 4.83

[3] RAG 검색 성공률
  질의 4개 (auto)
  recall@1 1.000 · recall@5 1.000 · MRR 1.000
```

라벨 정답셋으로 바꿔도 같은 6/6 이 나온다(인자 개수·반환형 일치율 1.000 추가).

## 한계 — 수치를 볼 때 감안할 것

- **예제 규모가 작다(API 6개).** 위 1.000 들은 "이 대상에서 오류가 없다"는
  뜻이지 일반적인 정확도가 아니다. 의미 있는 수치를 얻으려면 실제 대상
  프로젝트로 돌려야 한다.
- **헤더 전용 프로젝트는 자동 정답셋을 못 만든다.** CPython 헤더 214개처럼
  `static inline` 위주면 컴파일해도 심볼이 안 남아 `nm` 이 쓸 수 없고, 이
  환경에는 libclang 도 없다. 이 경우 라벨 파일이 필요하다.
  (해당 대상의 276개 탐지 = 실제 276개 확인은 별도 수동 대조 결과이며 이
  스크립트로 자동화된 수치가 아니다.)
- **자동 질의는 문서/제약조건이 있는 API 만 대상이 된다.** 그것들이 없는 API 는
  질의 자체가 만들어지지 않으므로, 검색 성공률은 "문서가 있는 API 기준"이다.
- `nm` 은 `static` 함수를 `t` 심볼로 잡지만, 인라인되어 사라진 함수는 놓친다.

## 테스트

```bash
python -m pytest tests/test_kb_eval.py -q
```

평가기 자체가 오류를 잡아내는지 확인하는 테스트를 포함한다 — 정답에만 있는
함수는 recall 을 떨어뜨리고, 정답에 없는 함수는 precision 을 떨어뜨리며,
인자 개수 불일치가 감지되는지 검증한다.
