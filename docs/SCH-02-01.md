# SCH-02-01 Logic Group 추출 + 패키징

통합 지식베이스(EXT-01-04)에서 **같은 상태를 공유하는 API 묶음**을 뽑아
`logosfuzz.common.models.LogicGroup` 으로 패키징한다.

```
KnowledgeBase ─▶ 상태 핸들/호출관계로 그룹화 ─▶ 실시간 신호 결합 ─▶ LogicGroup
                                                                    │
                          SCH-02-02(우선순위) · GEN(하네스) · EXE-04-03(타임아웃)
```

## 무엇을 "같은 상태"로 보는가

우선순위대로 세 단계다.

| 순위 | 기준 | `basis` |
| --- | --- | --- |
| 1 | 같은 **상태 핸들 타입**을 포인터로 주고받음 | `state_type` |
| 2 | 호출 관계로 연결됨 | `call_graph` |
| 3 | 같은 파일 | `file` |

**상태 핸들 = 프로젝트가 정의한 구조체에 대한 포인터.** 두 조건이 다 필요하다.

- 표준/외부 타입 제외 — `FILE *` 로 묶으면 무관한 API 가 엮인다.
- 스칼라 별칭 제외 — `Py_ssize_t *out` 은 결과를 받는 out-param 이지 상태가 아니다.
  타입 이름만 봐서는 구분이 안 되므로(`Py_ssize_t` 도 프로젝트 정의다)
  지식베이스가 기록한 `struct_types` 로 판정한다.

### 만능 타입 제외

`PyObject` 처럼 거의 모든 API 가 받는 타입으로 묶으면 그룹 하나에 API 가 전부
들어가 퍼징 단위로 쓸 수 없다. 검색에서 불용어를 빼는 것과 같은 이유로,
**전체 API 의 30% 초과를 차지하는 타입은 그룹 기준에서 제외**한다.
API 수가 20개 미만이면 비율이 요동치므로 적용하지 않는다.

CPython 헤더 기준 효과: 최대 그룹 **147개 → 53개**, 그룹 수 30 → 51.

## 실시간 신호 결합

`RealtimeSignal` 문서에 적힌 대로, 주석/규격서에서 타이밍 제약을 뽑아 그룹에
붙인다. **한 문장 안에** 신호 키워드와 시간 값이 함께 있어야 인정한다
(문서 전체를 한 덩어리로 보면 무관한 숫자가 엮인다).

| 키워드 | `kind` |
| --- | --- |
| `P2`, `P2*` | `uds_p2` |
| `watchdog`, `워치독`, `WDT` | `watchdog` |
| `CAN` + cycle/period/주기 | `can_cycle` |
| `control loop`, `제어 루프` | `control_loop` |

단위는 `ms` / `us` / `s` / `밀리초` / `초` 를 밀리초로 환산한다.
출처는 API 단위로 기록한다(`uds.c:uds_read_did`).

### EXE-04-03 연동 결과

`TimeoutManager` 는 그룹의 신호 중 **가장 빡빡한 주기**에 안전계수를 곱해
입력별 타임아웃을 정하고, 신호가 없으면 기본값으로 폴백한다.

```
헤더 주석: "UDS P2 서버 응답 시간은 50ms 이내여야 한다."

신호 없음 → per_input=1000ms (default)
신호 결합 → per_input=75ms  (dynamic; uds_p2 주기 50ms × 안전계수 1.5)
                             출처: uds.c:uds_read_did
```

## 사용법

```bash
python -m logosfuzz.schedule.logic_groups build --paths examples/uds --output build/groups.json
python -m logosfuzz.schedule.logic_groups build --kb build/kb.json -o build/groups.json
python -m logosfuzz.schedule.logic_groups show  --groups build/groups.json
python -m logosfuzz.schedule.logic_groups stats --groups build/groups.json
```

```python
from logosfuzz.knowledge.knowledge_base import KnowledgeBase
from logosfuzz.schedule.logic_groups import build_groups, to_logic_groups, to_group_map

kb = KnowledgeBase.load("build/kb.json")
groups = build_groups(kb)

to_logic_groups(groups)   # EXE/GEN 용 LogicGroup 목록
to_group_map(groups)      # SCH-02-02 rank_logic_groups 용 {group_id: [api_id]}
```

옵션: `--no-call-links` (핸들 타입만으로 묶기), `--no-priority` (시너지 계산 생략)

## 우선순위

SCH-02-02 를 임포트할 수 있으면 시너지 점수를 그룹 우선순위로 붙인다.
임포트할 수 없으면 `0.0` 으로 두고 조용히 넘어간다.

## 실제 코드 검증

| 대상 | 결과 |
| --- | --- |
| `examples/uds` | 그룹 1개(6 API), `uds_p2 50ms` 신호 추출 |
| CPython 3.12 헤더 214개 | 그룹 51개 / API 276개 / 최대 53 / 0.9초 |

CPython 에서 뽑힌 그룹 예: `PyLongObject`(15), `PyGC_Head`(6),
`_BlocksOutputBuffer`(6), `PyDictKeysObject`(3)

## 한계

- 상태 핸들이 없고 호출 관계도 없는 API 는 파일 단위로 떨어진다. 헤더 위주
  프로젝트에서는 `file` 기준 그룹이 많아진다(CPython 51개 중 39개).
- 함수 포인터로만 연결된 API 는 호출 그래프에 잡히지 않는다.
- 30% 임계값은 경험값이다. `extract_groups(..., ratio=)` 로 조절할 수 있다.
