# ANA-05-03: 지식 베이스 역피드백 및 하네스 재생성

> **선행 조사 결과**: ANA-05-01(LLM 기반 정탐/오탐 자동 판별)은 이 저장소에
> 구현되어 있지 않다 - `ana_05_02_cve_reporting/schema.py`의 `Verdict`/
> `TriageInfo`는 그 산출물을 담는 "그릇"으로만 존재하고, 판별 로직 자체는
> 없다. [`logosfuzz/control/hitl/hooks.py:87`](../logosfuzz/control/hitl/hooks.py)의
> `# TODO(ANA-05-03): 오탐 확정 → 지식베이스 역피드백 트리거` 주석이 정확히
> 이 기능이 연결되어야 할 지점을 가리키고 있었다. SCH-02-01(Logic Group
> 전용 패키징 모듈)도 없지만 `logosfuzz/common/models.py`의 `LogicGroup`
> 타입이 이미 그 계약을 대표하므로 스텁이 필요 없었다. GEN-03-01(초안 생성)은
> 재사용 불가능한 데모 스크립트뿐이라 어댑터로 대체했다. 자세한 내용은
> "스텁/어댑터" 절 참고.

## 기능 명세

| 항목 | 내용 |
|---|---|
| 기능번호 | ANA-05-03 |
| 기능명 | 지식 베이스 역피드백 및 하네스 재생성 |
| 기능설명 | ANA-05-01이 오탐(false positive)으로 확정한 크래시의 근본 원인을 LLM으로 분석하고, 그 결과를 지식베이스(API_METADATA) 변경 제안(diff)으로 만들어 사람 승인을 거친 뒤에만 반영한다. 승인되면 해당 Logic Group의 하네스를 새 지식으로 재생성하고 컴파일 성공까지 검증한다. |
| 처리내용 | 1) `rootcause.analyze_false_positive()` - ASAN 로그+콜스택+KB 컨텍스트를 추론형 LLM에 넣어 오탐 원인 요약 생성 → 2) `kb_feedback.propose_kb_update()` - 요약을 diff(`KBUpdateProposal`)로 만들고 (설정 시) 임베딩 계산, 아직 KB 미반영 → 3) `pipeline.run_ana_05_03()`이 `Checkpoint.KB_FEEDBACK`으로 HITL 게이트에 큐잉 → 4) 승인 시 `commit.apply_kb_update()`로 오버라이드 스토어에 upsert(`updated_at` 갱신) + `kb_feedback.rebuild_with_overrides()`로 재색인, 거부 시 `commit.discard_kb_update()`로 폐기(아무것도 안 썼으므로 롤백=무동작) → 5) 승인된 경우에만 `regenerate.trigger_regeneration()`이 새 KB 컨텍스트로 초안을 만들고 GEN-03-02 `SelfHealLoop`(`--max-round` 상한)로 컴파일까지 검증 → 6) 모든 단계 산출물을 `audit.AuditTrailStore`에 기록. |
| 연결기능 | **입력**: ANA-05-01 출력(스텁 `CrashRecord`, `verdict=FALSE_POSITIVE`인 것만 허용). **HITL**: CTR-06-02 `HITLManager`/`Checkpoint.KB_FEEDBACK`(신규, 항상 `MANUAL`). **재생성**: GEN-03-02 `SelfHealLoop`(기존 그대로 재사용). **출력**: 재색인된 `KnowledgeBase`(오버라이드 반영), `RegenerationRecord`, `AuditTrailStore` 감사 로그. |

## 스텁 / 어댑터로 대체한 부분

| 대상 | 상태 | 대체 방식 |
|---|---|---|
| ANA-05-01 | 미구현 | `models.CrashRecord`를 최소 입력 계약으로 정의(`verdict != FALSE_POSITIVE`면 즉시 예외). 실제 ANA-05-01이 생기면 그 출력을 이 타입에 채워 넣기만 하면 됨 |
| GEN-03-01 | 데모 스크립트뿐, 재사용 불가 | `regenerate.draft_via_llm()`이 KB 컨텍스트(+ 오탐 역피드백 노트)로 프롬프트를 구성해 `LLMClient.complete()`를 직접 호출 - "초안 생성"이라는 GEN-03-01의 책임만 별도 함수로 재구현. GEN-03-01이 실제로 구현되면 이 함수만 교체 |
| `API_METADATA.updated_at` | `src/knowledge_base.py` 문서 스키마에 없음 | EXT-01 코드를 건드리지 않기로 결정(설계 승인) → `kb_feedback.KBOverrideStore`가 api_id별로 별도 JSON 사이드 스토어에 관리. 조회 시 `rebuild_with_overrides()`가 원본 KB와 병합 |
| Vector DB upsert | `BM25Index`/`DenseIndex`는 append-only, in-place 갱신 불가 | 승인될 때마다 오버라이드가 반영된 문서 전체로 `KnowledgeBase`(=검색 인덱스)를 새로 만드는 **전체 재구축** 방식으로 대체(문서 수가 적을 때 전제). 대규모 환경에서는 증분 upsert가 가능한 실제 벡터 DB(Chroma/FAISS 등)로 교체 필요 - 알려진 제약으로 명시 |

## HITL 연동 (기존 CTR-06-02 재사용)

새 승인 큐를 만들지 않고 기존 `logosfuzz/control/hitl`을 확장했다(순수 추가, 기존 동작 변경 없음):

- [`logosfuzz/control/hitl/models.py`](../logosfuzz/control/hitl/models.py) - `Checkpoint.KB_FEEDBACK` 멤버 추가
- [`logosfuzz/control/hitl/policy.py`](../logosfuzz/control/hitl/policy.py) - 기본 정책에 `KB_FEEDBACK: CheckpointRule(Mode.MANUAL)` 추가(CVE_DISCLOSURE와 동급 - 항상 사람 승인)

## 트리거 정책: 즉시(reactive)

ANA-05-01이 오탐 판정을 내리는 즉시 `pipeline.run_ana_05_03()`을 호출한다고
전제한다. 크래시 발생 빈도 자체가 "이벤트당 1회 LLM 호출"의 자연스러운
rate-limit이고, 실제 KB/재생성 반영은 어차피 HITL 승인 없이는 일어나지
않으므로 배치로 모아 처리해도 얻는 지연 대비 이득이 크지 않다고 판단했다
(설계 검토 시 사용자 확인).

## 구조

```
logosfuzz/analyze/
  models.py       CrashRecord(ANA-05-01 스텁), RootCauseAnalysis, KBUpdateProposal,
                  ProposalStatus, RegenerationRecord
  rootcause.py     STEP 1: analyze_false_positive()
  kb_feedback.py    STEP 2: KBOverrideStore, propose_kb_update(), rebuild_with_overrides(),
                    embed_text()
  commit.py        STEP 3: apply_kb_update() / discard_kb_update()
  regenerate.py     STEP 4: draft_via_llm()(GEN-03-01 어댑터), trigger_regeneration()
                    (GEN-03-02 SelfHealLoop 재사용)
  audit.py         STEP 5: AuditTrailStore(crash_id/api_id/harness_id 역추적)
  pipeline.py       STEP 6: run_ana_05_03() 오케스트레이터
  tests/           단위 테스트 5개 파일 + 통합 테스트(defer/approve/reject 3가지 흐름)
```

## 완료 후 검증 체크리스트

| 항목 | 근거 |
|---|---|
| 동일 오탐 재발 방지 | `kb_feedback.propose_kb_update()`가 이전 오버라이드 텍스트를 유지·누적하고, `regenerate.draft_via_llm()`이 재생성 프롬프트에 그 노트를 반드시 포함시킨다. `test_pipeline_integration.py::test_root_cause_prompt_reused_in_regeneration_prompt`가 프롬프트에 원인 요약이 실제로 들어가는지 검증 |
| 무한루프 방지 | 재생성 자체는 GEN-03-02 `SelfHealLoop.max_round`(기존 상한)를 그대로 물려받는다 - 새 루프를 만들지 않았다. `test_regenerate.py::test_never_fixed_records_failure_without_infinite_retry`가 라운드 상한 준수를 확인 |
| `updated_at` 갱신/이력 정확성 | `KBOverrideStore.upsert()`가 매 승인마다 `updated_at`을 갱신하고 `AuditTrailStore`가 제안 생성/승인/거부 각 시점을 모두 별개 항목으로 남긴다. `test_kb_feedback.py`, `test_audit.py` |
| HITL 게이트가 실제로 차단 | 정책 기본값이 `MANUAL`이라 비동기(interactive=False) 모드에서는 `DEFER`만 반환되고 KB/오버라이드/재생성 어느 것도 실행되지 않는다. 거부 시에도 아무것도 쓰지 않는다(승인 전에 쓰지 않으므로 롤백=무동작). `test_pipeline_integration.py`의 `TestDeferredWhenNoHumanAvailable`, `TestRejectedFlow` |
| 다른 Logic Group/기존 KB 항목에 부작용 없음 | `rebuild_with_overrides()`는 오버라이드가 있는 `api_id` 문서만 수정하고 나머지는 원본 그대로 통과시킨다. `test_kb_feedback.py::test_untouched_documents_pass_through` |
| 재생성 하네스 컴파일 성공률 | `regenerate.trigger_regeneration()`이 반환하는 `RegenerationRecord.compiled_ok`로 확인 가능. `test_regenerate.py`, 통합 테스트의 `test_full_approve_flow` |
| LLM 호출 횟수 / Vector DB write / 지연 측정 | 이번 구현 범위에서는 자동 계측(메트릭 수집)까지는 넣지 않았다 - `ScriptedLLMClient.calls`로 호출 횟수는 테스트에서 직접 셀 수 있으나, 운영 환경에서의 비용/지연 계측은 후속 TODO로 남긴다 |
| `crash_id ↔ api_id ↔ harness_id` 트레이서빌리티 | `AuditTrailStore.for_crash()`/`for_api()`/`for_harness()`로 임의 방향 역추적 가능. `test_audit.py`, 통합 테스트의 트레이서빌리티 단언 |

## 알려진 제약 / 후속 TODO

- **비동기 승인 후 재개(resume) 경로 미구현**: `run_ana_05_03()` 한 번의 호출
  안에서 결정이 즉시 나야(정책 AUTO거나 `interactive=True`) STEP 4/5(커밋+재생성)까지
  이어진다. 정책이 `MANUAL`이고 `interactive=False`이면 `DEFER`만 반환하고
  끝난다 - 사람이 나중에 `HITLManager.decide()`로 승인해도 그것만으로는
  KB/재생성이 자동으로 이어지지 않는다. 별도 "결정 후 재개" 진입점(예:
  `logosfuzz kb-feedback resume <item_id>`)이 필요하며, 이는 제안(proposal)을
  `proposal_id`로 다시 조회할 수 있는 저장소가 추가로 필요해 이번 범위에서는
  뒤로 미뤘다.
- **LLM/Vector DB 호출 비용·지연 자동 계측 없음**: 위 체크리스트 항목 참고.
- **`sentence-transformers` 미설치 시 임베딩 없이 진행**: `src/rag_index.py`의
  기존 정책과 동일하게, 임베딩은 선택 사항이고 없으면 BM25 텍스트 검색만으로도
  `rebuild_with_overrides()`가 동작한다.
