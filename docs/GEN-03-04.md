# GEN-03-04: Harness Validation

> **선행 조사 결과**: 이 문서 작성 시점 기준으로 GEN-03-01(하네스 초안 생성)/
> GEN-03-02(컴파일 자가치유)/GEN-03-03(CAN/UDS mocking 삽입)은 저장소에
> 구현되어 있지 않다(디렉토리·클래스·함수 모두 없음). 요청받은 "기능번호/
> 기능명/기능설명/처리내용/연결기능" 표 포맷도 저장소 어디에서도 찾지
> 못했다 — 유일한 기존 스펙 문서인 `docs/EXE-04-01.md`는 자유서술형이며,
> 상세 설계는 "개인 Notion 페이지 참조"라고 명시되어 있다. 따라서 아래 표는
> 요청 포맷을 최대한 재현한 것이며, 원본 Notion 포맷과 다를 수 있다.
>
> 이런 이유로 GEN-03-04는 **GEN-03-01/02/03의 실제 구현에 의존하지 않고**,
> `logosfuzz/generate/contracts.py`에 정의한 계약(`HarnessArtifact` /
> `RegenerateCallback`)만 신뢰하도록 구현했다. GEN-03-01/02/03이 이후
> 구현되면 이 계약에 맞춰 값을 넘기기만 하면 별도 수정 없이 연결된다.

## 기능 명세

| 항목 | 내용 |
|---|---|
| 기능번호 | GEN-03-04 |
| 기능명 | Harness Validation (하네스 검증 게이트키퍼) |
| 기능설명 | GEN-03-01~03을 통과한(컴파일 성공) 하네스가 ECU/네트워크 인터페이스 미가상화 등 "환경적 결함"으로 즉시 종료되는 오탐 하네스인지, 본 퍼징 캠페인(EXE-04) 투입 전 수 초~수십 초 내 짧게 걸러낸다. |
| 처리내용 | 1) dry-run 스모크 테스트(`-runs=N`, 기본 100)로 즉시 crash/abort/segfault/hang 여부 확인 → 2) 같은 실행에서 수집된 edge coverage가 임계치(기본 1) 이상인지 확인, 0이거나 미만이면 "타겟 API 미도달"로 실패 → 3) 실행 로그에서 GEN-03-03이 삽입한 CAN/UDS mock 심볼 호출 흔적을 grep(`[MOCK-CALL] <symbol>` 컨벤션) → 4) (선택) 하네스 소스와 API 시그니처를 비교하는 정적 리뷰. 하나라도 실패하면 그 지점에서 중단하고 실패 사유를 `FeedbackPayload`로 만들어 상위 재진입점에 전달, `--max-round`까지 재시도 후 최종 실패 처리. |
| 연결기능 | **입력**: GEN-03-02(컴파일 자가치유) 산출물 — `HarnessArtifact` 계약. **출력 성공 시**: EXE-04-01(`logosfuzz fuzz`)이 소비할 `LogicGroup`으로 변환 가능한 검증된 하네스. **출력 실패 시**: GEN-03-01(재생성) 또는 GEN-03-02(재수정)로 `FeedbackPayload` 피드백, `RegenerateCallback` 계약으로 재진입. **결과 저장**: `out/gen_validation_summary.json`, `out/logs/gen_validation/<group>.json` — ANA 단계가 정탐/오탐 판별 시 참조 가능하도록 `ana_05_02_cve_reporting`의 `harness.gen_model` 필드 컨벤션과 나란히 두도록 설계. |

## 검증 4단계 상세

| 단계 | 실패 조건 | 실패 시 분류 |
|---|---|---|
| 1. dry-run 스모크 테스트 | `-runs=N` 실행 중 비정상 종료(exit≠0) 또는 하드 타임아웃 초과 | crash / hang |
| 2. 커버리지 임계치 검사 | 1번 실행에서 관측된 edge coverage(`cov:` 최댓값)가 0이거나 설정 임계치 미만 | 타겟 API 미도달 |
| 3. Mocking 호출 트레이싱 | `HarnessArtifact.expected_mock_symbols` 중 로그에서 호출 흔적을 찾지 못한 심볼 존재 | 환경 미가상화 |
| 4. (선택) 정적 리뷰 | 하네스 호출부와 `ApiSignature.param_types` 인자 개수 불일치 | 하네스 코드 결함 |

1~3단계는 **동일한 dry-run 실행 로그 하나**를 재사용한다(추가 실행 없음) —
"수 초~수십 초 내 완료"라는 성능 제약을 지키기 위함이다.

## CLI 통합 방식: `generate` 내부 단계 vs 별도 `validate` 서브커맨드

| 비교 | `generate` 내부 단계로 흡수 | 별도 `logosfuzz validate` 서브커맨드 (채택) |
|---|---|---|
| 전제 조건 | `generate` 명령이 이미 존재해야 함 | 독립적으로 지금 바로 붙일 수 있음 |
| 재검증(재실행)만 하고 싶을 때 | 생성 파이프라인 전체를 다시 돌려야 함 | `logosfuzz validate`만 재실행 가능 |
| CI/사람이 수동으로 "이 하네스 지금 상태로 퍼징해도 되나?" 확인 | 불가능(생성과 묶여 있음) | 가능(컴파일된 산출물만 있으면 됨) |
| GEN-03-02의 컴파일 자가치유 루프와의 관계 | 컴파일 성공 직후 자동 연쇄 → 응집도는 높지만 실패 시 "컴파일 문제인지 검증 문제인지" 로그가 섞임 | 별도 단계라 실패 로그가 컴파일/검증으로 명확히 분리됨 |

**선택: 별도 서브커맨드(`logosfuzz validate`).** 근거:

1. `generate` 서브커맨드 자체가 이 저장소에 아직 없다 — GEN-03-01/02/03이
   구현되기 전까지는 "내부 단계로 흡수"할 대상이 존재하지 않는다. 반면
   `validate`는 `HarnessArtifact` 계약만 있으면 되므로 지금 독립적으로
   동작·테스트할 수 있다.
2. EXE 파트(`logosfuzz fuzz`)도 이미 `--harness-dir`/`--groups` 로 GEN
   산출물을 "느슨하게" 소비하는 구조다(같은 프로세스가 아님). GEN-03-04도
   같은 패턴(컴파일된 산출물 + 매니페스트 JSON을 입력으로 받는 독립 명령)을
   따르는 것이 저장소 컨벤션과 일관적이다.
3. 검증은 EXE-04(본 퍼징, 분 단위)와 성격이 다른 "빠른 게이트"(초 단위)다.
   별도 명령으로 분리해 두면 CI 파이프라인에서 "컴파일 → 검증(빠름) →
   (필요 시에만) 본 퍼징(느림)" 단계를 독립적으로 스킵/재실행하기 쉽다.
4. `generate`가 실제로 구현되면, 그 내부에서 `logosfuzz.generate.feedback_loop.
   run_validation_pipeline()`을 **함수로 직접 호출**하면 된다 — CLI 명령을
   또 만들 필요 없이 동일 로직을 재사용할 수 있으므로 "흡수 vs 분리"가
   상호 배타적이지 않다.

## CLI

```
logosfuzz validate --harness-dir <dir> --output <dir> \
    [--manifest manifest.json] [--runs N] [--timeout sec] \
    [--coverage-threshold N] [--max-round N] [--static-review]
```

`--manifest` JSON 형식 (미지정 시 `--harness-dir` 안의 실행 파일을 각각
그룹으로 자동 인식하되, mock 트레이싱/정적 리뷰 단계는 생략됨):

```json
[
  {
    "group_id": "lg_1_uds",
    "harness": "harnesses/lg_1_uds",
    "source": "harnesses/lg_1_uds.c",
    "corpus": "corpus/lg_1_uds",
    "expected_mock_symbols": ["mock_can_recv", "mock_uds_send"],
    "api_signatures": [
      {"name": "uds_read_data", "param_types": ["int", "uint8_t*", "size_t"]}
    ],
    "gen_model": "gpt-4o-mini"
  }
]
```

종료 코드: `0` 전체 통과, `3` 검증 실패 그룹 존재(→ GEN-03-01/02 재시도
또는 사람 확인 필요), `1` 실행 오류(하네스 없음 등).

## 구조

- `logosfuzz/generate/contracts.py` — `HarnessArtifact`, `ApiSignature`,
  `FeedbackPayload`, `RegenerateCallback` (GEN-03-01/02/03과의 계약)
- `logosfuzz/generate/validation.py` — 4단계 검증 로직 + `validate_harness()`
- `logosfuzz/generate/llm_review.py` — 정적 리뷰 `StaticReviewer` 프로토콜 +
  `MockStaticReviewer`(정규식 기반 인자 개수 비교, 실제 LLM/Vector DB 연동 전 임시 백엔드)
- `logosfuzz/generate/feedback_loop.py` — `validate_with_retry()`(재시도 루프,
  `--max-round` 상한), `run_validation_pipeline()`(다중 그룹 오케스트레이션 +
  요약 JSON 저장 + 콘솔 출력)
- `logosfuzz/cli.py` — `validate` 서브커맨드, `load_harness_manifest()`

## 산출물

`out/gen_validation_summary.json`(전체 요약: 성공/실패 그룹 수·목록),
`out/logs/gen_validation/<group>.json`(그룹별 라운드 이력 + 각 단계 상세
로그) → EXE-04-01 투입 여부 판단 및 ANA 단계의 역피드백 참고 자료로 사용.

  인자 "개수" 불일치만 잡아내며 타입 검증은 하지 않는다.
- **mock 호출 트레이싱 컨벤션 신규 정의**: GEN-03-03이 없어 기존 네이밍
  규칙이 없었으므로, `[MOCK-CALL] <symbol>` 형태로 stdout/stderr에 로그를
  남기는 컨벤션을 이번에 새로 정의했다. `logosfuzz/execute/sanitizer.py`의
  `classify_sanitizer_error()`가 이미 로그 텍스트에 `"mock"` 토큰이 있으면
  `mocking-fail-fp`로 분류하는 규칙과도 호환된다.
- **coverage 파싱은 libFuzzer 텍스트 출력(`cov:`) 기반**: AFL++ 대상이나
  `llvm-cov` 정밀 계측(EXE-04-04 연동)은 다루지 않는다.
