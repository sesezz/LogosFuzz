프로젝트 개요

1. 개발 배경

  • 오픈소스 공급망 보안 위험: 대부분의 SW가 C/C++ 오픈소스 라이브러리를 재사용하므로, 라이브러리 하나의 결함이 의존하는 SW 전체로 확산
  • 메모리 안전성 결함: 길이, 할당 크기, 객체 수명 같은 경계 조건은 정상 기능 시험으로 놓치기 쉬움
  • 퍼징의 높은 진입장벽: OSS-Fuzz는 1,000개 프로젝트에서 10,000건 이상의 취약점을 발견했지만, 수작업 하네스와 복잡한 빌드 설정으로 일반 조직의 도입이 어려움
  • 자동차와 임베디드의 시급성: SDV의 진단, 로깅, 통신이 C/C++ 오픈소스에 의존하며 UN R155(CSMS) 규제 준수가 의무화됨
주요 사례내용KISA 보안약점
Heartbleed (2014)메모리 경계 검증 누락 → 대규모 정보 유출메모리 버퍼 오버플로우
BadAlloc (2021)할당 크기 오류 → 임베디드 SDK 등 CVE 25개 이상정수형 오버플로우
Redis CVE-2025-49844조작된 Lua 스크립트의 use-after-free → 원격 코드 실행해제된 자원 사용

2. 기존 방식의 한계

  • 하네스와 빌드 수작업: 프로젝트당 수 시간의 수작업과 고도의 전문지식 필요
  • C++와 Bazel 구조 복원 실패: score/json 기준 106개 파일이 있어도 API 0개 추출
  • 환경 의존 오류: 하드웨어와 외부 함수 부재로 링크 실패와 가짜 크래시 발생

3. LogosFuzz 개발 목표

“대상 프로필 1개 설정, 명령어 한 줄로
지식 추출부터 크래시 판별까지 자동 수행”
$ logosfuzz run --profile targets/libsndfile.json
  --budget 600 -o out/libsndfile
  • 소스, 주석, 빌드 정보에서 API 제약을 추출해 지식베이스 구축
  • 연관 API를 상태 기반 로직 그룹으로 묶어 하네스 생성
  • 컴파일/링크 오류 분류 기반 자가치유, 누락된 HAL 함수 자동 Mock 주입
  • Docker 격리 퍼징, ASan/UBSan 메모리 오류 탐지
  • 규칙 기반 판별과 사람 승인을 거쳐 오탐을 지식베이스에 역피드백

시스템 설계

1. 시스템 구성

입력오픈소스 소스코드, 대상 프로필(targets/*.json), 빌드 어댑터(Bazel, CMake, prebuilt)
AI와
지식 계층		LLM(GPT-4o) 하네스 생성과 퍼징 오류 자가치유, 지식베이스 + BM25 RAG, 규칙 기반 크래시 판별 + 예외 케이스 LLM 보완
코어 엔진정적 분석(Bazel query, compile_commands, libclang AST), 동적 퍼징(libFuzzer), 오류 탐지와 계측(ASan, UBSan, llvm-cov)
보안 경계Docker 격리 실행(네트워크 차단, 권한 최소화, 자원과 파일 보호), HITL 승인 게이트(지식베이스 변경과 취약점 공개는 사람 승인 후 반영)

3. 핵심 기술

기술설명
다중 소스
지식 추출		AST, 주석, 분기문에서 NULL 검사, 버퍼-길이 쌍, 값 범위, 해제 책임을 추출해 신뢰도와 함께 저장하고 하네스 프롬프트에 주입
빌드
자가치유		컴파일 오류와 3대 링커 오류(미정의 심볼, 중복 정의, 라이브러리 누락)를 분류해 LLM으로 수정하고, 미정의 HAL 함수는 weak 스텁 자동 생성
크래시 판별과 역피드백스택 서명 중복 제거와 함수별 에러 반환 규격 기반 규칙 판별, 신뢰도 0.8 미만은 사람 검토와 증거 주입 LLM 판별로 정확도 10% → 85% (dlt-daemon 크래시 20건 기준)

보안약점 예방 설계

1. 설계 원칙: 외부 코드, LLM 생성 코드, 크래시 입력은 신뢰하지 않음

원칙적용 내용
신뢰 경계 분리LLM 생성 코드와 퍼징 입력은 격리 컨테이너에서만 실행 (--network none, cap-drop ALL, 자원 상한, 읽기 전용 마운트)
명령 문자열 미사용외부 도구는 인자 리스트로만 호출 (shell=True, os.system 0건), LLM 출력은 eval/exec 없이 C 코드로만 컴파일
사람 승인 게이트KB 변경과 취약점 공개는 HITL 승인 필수, 락과 원자적 쓰기의 append-only 감사 로그
비밀정보와 출력 보호API 키는 환경변수로만 수신, HTML 리포트의 모든 문자열 esc() 처리

결론

1. 기대효과

  • 하네스 작성 자동화: 프로필 1회 작성으로 하네스 수작업을 대체하고 반복 빌드 오류 수정 시간 단축
  • 탐지 범위 확대: 자동 스텁으로 하드웨어 없이 임베디드 코드를 탐색하고, 에러계약 판별로 실제 취약점 후보에 집중
  • 오픈소스 공급망 검증: 도입 전 보안 검증 자동화, UN R155 테스트 증거 축적

2. 향후 계획

  • 기술 고도화: ASan 크래시 위치 복원 후처리, 생성 함수 누락 로직 그룹 보완
  • 검증 자동화: GitHub Actions 연동 CI 보안 검증, 생성 하네스 기반 실측 대상 확대
  • 적용 범위 확대: 바이너리 대상 퍼징, 다양한 CPU 아키텍처 지원
